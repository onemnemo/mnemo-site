The layers

Mnemo is built as strict layers. Contracts point inward, implementations point outward, and nothing reaches across.

Mnemo.Core Contracts: service interfaces, domain models and pure logic. Depends on almost nothing.
Mnemo.Infrastructure Implements those contracts: SQLite storage, the FSRS scheduler, Markdown conversion, spellcheck, import and export.
Mnemo.Host An ASP.NET Core minimal API on loopback, plus the native window. Wires up every service and exposes it under /api.
mnemo-web The React and TypeScript app, built with Vite. Holds presentation state only. Business rules stay in C#.

A change that spans layers lands in that order: the interface in Core, the implementation in Infrastructure, the endpoint in Host, and the screen in mnemo-web.

Modules

Features are modules that implement IModule, with hooks for services, translations, shortcuts, sidebar entries and widgets. They're found by reflection, so adding a feature never means editing a central list. Mnemo.Host/Composition/HostComposition.cs is where they get wired up.

The local API

The UI and the backend are one app on one machine. Kestrel binds to 127.0.0.1 only, and every request except the health check carries a bearer token made fresh at each launch. In production the host writes the token into the page it serves. In dev it goes through the Vite proxy.

A strict content security policy with a nonce per launch blocks any script the app didn't ship, and connect-src 'self' keeps requests on the host.

Push from server to client is one SSE stream at GET /api/events, used for things like toasts and shutdown. It never replays, so nothing should treat it as the source of truth.

Closing the window doesn't kill a save halfway. The host sends a shutdown event, the UI gets a moment to flush, then the app closes. Pressing close twice skips the wait.

Adding an endpoint

Endpoints are minimal API handlers that live with their feature, like Mnemo.Host/Flashcards. Copy an existing feature folder: contract in, service call, DTO out, nothing clever in the handler.

Where data lives

Everything sits in one data folder, centred on a single SQLite file, mnemo.db, with images and attachments stored as files beside it. The database holds three shapes of data:

  • A key value table of JSON documents behind IStorageProvider, for settings and most module state.
  • A relational flashcard schema with an append only review log, in WAL mode with one writer.
  • Note bodies, written with optimistic concurrency. A stale write gets a 409 with the stored version.

Migrations run at startup, before the API takes its first request.

Packages, backups and trash

The .mnemo format is a zip with a manifest.json and a folder per module. Adding something exportable means writing a payload handler, not a new format. Markdown, CSV and Anki are adapters on top.

A .mnemo-backup is a consistent snapshot of the whole profile. Restore is staged and swapped in on the next start, with the old data moved to restore-recovery first.

Deleting leaves rows in place. Each module records the item in a shared trash ledger, kept for 30 days, and a background task sweeps expired entries.
