Contributing

From a first issue to a merged pull request.

Find something to work on

Browse the issue tracker. The good first issue label is picked for newcomers. Comment on an issue before you start, so nobody does the same work twice. For big features, architecture changes or major UI work, open an issue first. Small fixes can go straight to a pull request.

The coding standard

The standard lives in the repository under standards/, split by topic, and the repo always wins over this page. The rules reviewers catch most often:

  • No em or en dashes anywhere a person can read: comments, commits, translations, release notes.
  • No TODO, FIXME or HACK. Write the follow up into future-review/ instead.
  • Every string a person can read is a translation key, in English, German, Spanish, Japanese and Norwegian.
  • A performance number needs proof of correct output from the same run.
  • On the .NET side, all I/O is async and cancellable, and .Result and .Wait() are banned.

Commits

Write type(scope): subject, lowercase and in the imperative:

feat(notes): teach the sidebar tree to drag folders into folders
fix(host): answer 409 with the stored version on stale note writes

Types in use are feat, fix, perf, refactor, test and chore. A feature usually lands in two or three commits along its natural seams. Build and test before every commit, and never rewrite a commit that's already pushed.

Sign off

You keep your copyright, and contributions are under GPLv3. Sign each commit with git commit -s. That sign off is the only trailer a commit carries, so no co author or AI attribution lines.

Pull requests

  • Keep it to one concern, with no drive by reformatting.
  • Say what changed and why, link the issue, and add screenshots for anything visual.
  • Run the tests before you push.

Review asks three things: does it solve a real problem, does it match the code around it, and does the app still behave honestly and predictably.

Something unclear or missing? Tell us on GitHub.
